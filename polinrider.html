What the scanner detects

Config injection — PolinRider / auth-con-firm hides a remote-code loader in postcss, next, vite, tailwind, eslint and similar configs: a ~30 KB obfuscated blob after whitespace, or an atob+fetch loader paired with a committed .env.

VS Code autorun (TaskJacker) — a .vscode/tasks.json with "runOn":"folderOpen" and a hidden presentation that runs curl | bash or node on a disguised file the moment the folder opens; settings.json may pre-enable task.allowAutomaticTasks.

Variants — the original rmcej%otb%/_$_1e42 loader, the rotated Cot%3t=shtP/MDy build, variant A (global.i='A8-…', also injected into migrations/*.js), and the 2026-10 B2 wave (global['!']='9-6516-2' with a javascript-obfuscator _0x… string table, forged commits from a +0200 timezone, jest.config.js, fa-solid-900.woff2 inside decoy Font Awesome folders). Exact known payload files are also matched by SHA-256.

Any build config — every *.config.js/ts (vite, vitest, jest, next, postcss, playwright, babel …), .*rc.js and gulp/grunt/knex files are inspected, not just a fixed list. Entry points — the same loader spliced into src/main.ts, index.ts, App.js or server.js (root or under src/); small entry files are always content-scanned and cleaned by cutting the loader block, never by restoring old application code. Root dropper + script chain — a root-level api.js (~29 KB, one padded line) with package.json scripts rewritten to node api.js && …; the dropper is deleted and the chained segment removed from the scripts.

Fake fonts — JavaScript stored in .woff2/.ttf/.otf/.eot or invented extensions such as .llf under public/ or assets/ (real binary fonts pass a magic-byte check). Artifacts — the propagation script temp_auto_push.bat (a near-certain sign of past compromise). npm vector — known malicious dependencies and install-time lifecycle scripts in package.json. Signals are indicators for review; large legitimate configs can also be flagged.

A few things to know

How are fixes made?

The tool reads a file through the GitHub Contents API. For config files, it searches up to 30 historical commits for a clean version; otherwise it reconstructs the file by stripping suspicious long lines. For .env files, it removes the known dropper line. For package.json, it removes known malicious dependencies and install-time lifecycle scripts. Weaponized .vscode/tasks.json, fake font payloads and temp_auto_push.bat are deleted (there is no clean version to restore). Flagged settings.json loses only the worm's keys (task.allowAutomaticTasks, the decoy tasks block, terminal.integrated.hideOnStartup) and is deleted when nothing legitimate is left; entry files and root scripts have the loader line or block cut out; launch.json is left for manual review. Owners or repositories listed under Exclude on the scan page are never scanned and never fixed, even inside a ticked scope. A live fix writes a normal commit to the selected branch. Review the restore method carefully: a historical version may omit recent legitimate changes.

Can I stop and resume?

Yes. Completed repositories are journaled in local storage. Stop leaves unfinished repositories pending, so Resume checks them again. Open this same file in the same browser to return to your saved scan. Keep the file at the same location; file-URL storage behavior can differ between browsers.

Where does my data go?

Scanning and fixing communicate directly with api.github.com. Repository code is read as text and never executed. Your token stays in memory unless you choose to remember it. The optional “Load from URL” action fetches only the IOC URL you provide, without your GitHub token.

What access does my token need?

Use a classic token with the repo scope, or a fine-grained token covering your target repositories with Contents read permission for scanning and read/write for fixing. Organization approval, SSO, branch protection, or repository rules may restrict access or commits.

What if GitHub limits my requests?

The API meter tracks the remaining request budget. The tool waits and retries rate-limited requests automatically. Lower concurrency to reduce simultaneous requests. Unverified results indicate incomplete checks and should be scanned again.
